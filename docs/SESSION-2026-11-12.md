# Bring-up session, 12 November 2026

First session with the reorganised repo and the robot together. The point
was to stop guessing at constants and measure them.

## What is now known, not assumed

**Drive directions — fixed and verified twice.**
Three of the four constants in `MecanumDrive` were wrong. The code assumed
the usual mirrored pair (left side reversed, right side forward); this
robot has only the front right reversed. Driving on the old values would
have made it turn instead of go straight.

| Wheel | Native spin | Constant |
|---|---|---|
| front left | forward | `FORWARD` |
| front right | **backward** | `REVERSE` |
| back left | forward | `FORWARD` |
| back right | forward | `FORWARD` |

Confirmed on the floor: forward, backward and both strafes all produce
the correct mecanum sign pattern in the log.

**IMU orientation — measured.**
The Control Hub is mounted vertically on edge, ports up, so the old
`LOGO_DIR = UP` / `USB_DIR = FORWARD` could not have been right. Test 4
gave +58 degrees at a quarter turn left, and three turns across the
session read +150, +101 and -117 matching their directions.
`LOGO_DIR = LEFT`, `USB_DIR = UP`. Field-centric driving is safe to
enable; it is off by default.

**Catapult jog power.**
0.25 only whined and twitched against a loaded arm. 0.55 moves it.

## What is blocked

**The catapult encoder cable is missing.** Not unplugged -- absent. 668
log samples all read exactly 0 ticks while the motor drew up to 4 A and
the arm visibly moved.

Needed: a 4-pin **JST PH** (hub end) to **JST XH** (motor end) encoder
cable. goBILDA 5202 motors use XH; the REV hub uses PH. About $3-4.

- 150mm: https://www.servocity.com/encoder-cable-150mm-length-4-pos-jst-ph-mh-fc-to-4-pos-jst-xh-mh-fc/
- 300mm: https://servocity.com/4-pos-jst-ph-mh-fc-to-4-pos-jst-xh-mh-fc-adaptor-300mm-length
- 600mm: https://servocity.com/4-pos-jst-ph-mh-fc-to-4-pos-jst-xh-mh-fc-adaptor-600mm-length

Measure the run from the motor to the Expansion Hub before ordering. The
drive motors may also lack encoder cables -- they run
`RUN_WITHOUT_ENCODER` so it never showed. Worth checking and ordering
spares.

Until the cable arrives, these stay as placeholders and **must not be
trusted**: `RELEASE_POSITION` (hardcoded 300), `STALL_CURRENT_A` (99.0,
which disables stall detection), `OVERSHOOT_COMP`.

`CatapultOpMode` as it stands would believe the arm is permanently at 0
ticks, never reach its release point, and sit firing until the timeout.
**Do not run it on the robot until the encoder works.**

## The thing worth remembering

Most of tonight's lost time came from one pattern: **the robot reports
success while doing nothing.** A build "succeeded" and produced a
166-byte jar with no classes in it. A rebuilt class was ignored because
the old one was already loaded. An op mode ran for 153 seconds in the
wrong test because a bumper press never registered.

None of these announced themselves. Check that op modes actually
registered before believing a deploy worked.
